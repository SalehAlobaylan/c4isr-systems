# Implementation plan for simulation preparation

**Proposed · 18 November 2026.** This plan turns the eight workstreams in the November 15 review into deliverable changes. The first user is a geographic analyst or application developer who receives an environment, checks whether it can answer a question, and reads the permitted values independently. The first delivery target is a desktop or headless reader for one bounded area. Riyadh is the first real candidate. An owned fixture allows development and CI to proceed while release decisions, data rights and independent measurements are pending. [Preparation review](SIMULATION_PREPARATION_REVIEW_2026_11_15.md) · [Product scope](../../../EMAD_CURRENT_SCOPE.md)

**First implementation change.** Check in a small owned package with a native raster containing a valid zero, a nonzero value and a masked cell. Give its area a hole and include a vector feature with a known source ID. Store its expected answers and trusted digests separately from the reader. Wire the existing prepared-archive verifier to a proposed CLI that lists the members and reads one native cell. Run it with networking disabled in the existing geospatial tooling environment. This change needs neither a database migration nor new provider access. It establishes the common fixture for the four workstreams in milestone 1. ## P01 — Consumer requirements and capability checks

**Analysis.** Build preflight already checks whether an environment can be prepared. The release quality report exposes the profile digest, source declarations, frame controls and coverage counts. A consumer needs a different answer once the release exists. For example, a release can describe a surface well enough for visual inspection while providing insufficient evidence for independently checked ground elevation. Counts alone cannot establish coverage at a requested point. [Current quality report](../../../internal/geoenv/profile_quality.go) · [Environment API](../../../api/openapi/environment-library.yaml)

**Implementation.** The data-contract and backend owners deliver this in two changes.

1. Define a versioned requirement document and reason codes. Include intended operation, exact release and area, required and optional representations, requested time or allowed source periods, units/datum, coverage, quality evidence and resource limits. Start with two worked requests on the same fixture. One accepts native surface inspection with unknown physical accuracy. The other requires independent ground measurements. Use the release's actual masks or coverage evidence for spatial predicates.
2. Add a release-scoped suitability operation to the existing Go API and OpenAPI client. Implement the same decision rules in the offline reader using shared input/output examples. Return a result per requirement and an overall result. A proven violation makes a required item **unsupported**. Missing evidence makes it **unqualified**. All required items must pass for **supported**. Optional omissions appear separately. Attach the evidence digest and reason to each decision. Apply access checks before returning scoped metadata. Online use reevaluates current rights. Offline evaluation states which issued terms and expiry it used.

**Acceptance.** Run both consumers against the same known-answer cases. Include acceptable imagery with missing optional weather, required ground absent, ground present with unknown accuracy, incompatible source years, and an area partially outside valid coverage. Withdrawing a grant prevents a new authorized read. Correcting an assessment produces a new decision that identifies the new evidence. **Depends on** P04 fixture definitions initially and reviewed P04 assessments for any real accuracy claim.

## P02 — Canonical feature semantics and topology

**Analysis.** The OSM extractor reads way nodes, clips the geometry and writes source ID and tags to GeoPackage. A consumer can recover the shape and tags, but the prepared file lacks original node memberships. Crossing lines on a map therefore cannot establish a shared junction. A source feature may also appear in several components of a release. Riyadh already has typed provider dimensions and distinct modeled building centroids. [Vector preparation](../../../scripts/data/environment_library.py) · [Dimension preparation](../../../scripts/data/environment_enrichment.py) · [Riyadh audit](../../../docs/implementation/RIYADH_ENVIRONMENT_ENRICHMENT.md)

**Implementation.** Geospatial engineering first delivers a feature dictionary and reader for existing packages. Expose source/edition, layer, source feature ID, component, canonical geometry, raw tags and dimension origin. Return all clipped parts for a source feature. Keep source identity and individual part identity distinct. Preserve polygon holes and tag units. Consumers can distinguish a missing tag, an unparseable tag and a sourced value.

For new builds, retain evidence of source relationships alongside the geometries in a versioned companion artifact. Record source node membership where the admitted original supplies it, component-boundary cuts and omitted or ambiguous relationships. Use a new recipe/toolchain digest. Earlier releases can disclose which topology is unknown. Reprocessing an authorized original produces a separately identified result. The first delivery is a diagnostic view for geographic inspection. Extend network coverage only when a consumer requests it and the source supports it.

**Acceptance.** An owned fixture includes two crossing lines with different node IDs, two ways sharing one node, a feature clipped by the area, a multipart footprint with a hole, and an unsupported dimension string. A fresh reader reproduces each distinction and retrieves the same feature after a display simplification. Keep inferred centroid heights separate from footprint dimensions. **Depends on** P04 known answers. P03 can ship basic feature lookup before the new relationship artifact is available.

## P03 — Native environment queries

**Analysis.** Preparation preserves raster registration, masks, source attributes and transform controls. The viewer's vector drape applies a documented 0.6 m display offset. Sampling those rendered vertices would change the answer to a native elevation query. The existing mosaic code also demonstrates why grid registration, overlap and datum must be checked before combining tiles. [Native grid handling](../../../scripts/data/display_surface_mosaic.py) · [Display data contract](../../../internal/geoenv/display_layers.go) · [Coordinate transforms](../../../internal/simulation/spatial.go)

**Implementation.** Geospatial and backend engineering deliver the reader in the existing Python geospatial environment. First support member inventory and exact native-cell reads, then point-to-cell lookup, feature-by-ID, bounded area selection and frame conversion. Use member metadata for row order, registration, scale, offset, units and validity. Define the edge convention and deterministic treatment of shared boundaries in the contract. Keep categorical codes exact. Resolve a height conversion only when the input datum, conversion method and required grid are available. Explicitly request surface or modeled ground.

Return a value or a documented outcome such as outside-area, masked, unsupported conversion or conflicting overlap. Include member digest, component, native index or feature ID, unit, method and assessment reference where present. A measured zero must survive serialization. Give the installed workflow the same request/result contract. For the initial implementation, run GEOS/GDAL-dependent reads in a bounded worker process using the same reader as the CLI. The Go API validates scope, request size and release pin, submits the work and rechecks access on result retrieval. Cap area, result count, bytes and execution time. Use an independently computed oracle to test both entry points.

**Acceptance.** Check a valid zero, mask, hole, exact seam, conflicting overlap, clipped feature, axis ordering, unit conversion and missing geoid. A known native sample is unchanged when a display layer is enabled or disabled. Repeating a supported query on the same bytes yields the same scientific value and lineage. **Depends on** P04 fixtures and P05 local verification. P02 supplies richer feature semantics incrementally.

## P04 — Reference area and independent validation

**Analysis.** The Go release validator and the Python verifier both require the v1 physical accuracy field to be `UNKNOWN`. The 1 mm numerical transform check answers a different question from accuracy on the ground. Riyadh's modeled ground and surface have overlapping source ancestry, and its modeled building-height points do not measure footprint heights. The smallest compatible change is a separately versioned assessment tied to the release and member. [Release validator](../../../internal/geoenv/releases.go) · [Archive validator](../../../scripts/data/environment_library.py) · [Riyadh measurements and limits](../../../docs/implementation/RIYADH_ENVIRONMENT_ENRICHMENT.md)

**Implementation.** Quality engineering owns the analytical fixture corpus. Data stewardship and a geospatial reviewer own physical evidence.

1. Publish redistributable fixtures and expected values calculated independently of the implementation under test. Include scale and offset, opposite axis directions, seams, holes and a second local origin. Version fixtures and answers together and retain the derivation of each expected value.
2. Inventory potential independent controls for a small Riyadh subarea. Record datum, units, acquisition date, uncertainty, spatial coverage, provenance, rights and shared ancestry. For the proposed use, specify sampling coverage, statistic and tolerance before looking at the results. Hold out validation controls from any fitting or adjustment. If suitable controls are unavailable, publish the precise evidence gap and qualify the uses that can be established.
3. Add scoped assessment storage and retrieval in the geographic module through an additive migration. Key each immutable record to the release digest, member digest, area, method, control-set digest, statistic, uncertainty, use and reviewer decision. Record corrections as superseding records. Enforce source visibility on the evidence and the released summary. P01 pins the particular assessment used so that an older decision can be explained.

**Acceptance.** A second reader reproduces the analytical controls. An independent reviewer can reconstruct a physical result from admitted control data, or record which claim remains unqualified. A subarea assessment cannot qualify the whole city, and a result for one member cannot be applied to a replacement member with a different digest. The original v1 ZIP verifies byte for byte. **Depends on** owned data for CI and suitable independent data only for the physical claim.

## P05 — Independent consumer kit and offline handoff

**Analysis.** The receiver discovers a released package and saves its verified ZIP. It streams selected displays through a hash check and records their identities, but does not save the display bytes. The geographic handoff verifier expects those bytes locally. The gap is assembling exactly what a selected consumer needs and can lawfully receive. The archive verifier already dispatches across package profiles. The enrichment verifier temporarily changes module bindings for a single command, which matters if readers are served concurrently. [Receiver](../../../scripts/ops/receive_environment_release.py) · [Archive verifier](../../../scripts/ops/verify_environment_rebuild.py) · [Handoff verifier](../../../scripts/ops/verify_geographic_handoff.py) · [Enrichment processor](../../../scripts/data/environment_enrichment.py)

**Implementation.** Backend and tooling owners deliver a native-only kit first, followed by optional display and observation dependencies.

1. Define a versioned inventory with release and area identities, required member and archive digests/lengths, selected displays or handoff, reader compatibility, purpose, terms and expiry. Obtain its trusted digest from the authorized release or issuance record through a separate trusted channel. Use the existing source admission and output permissions for the requested operation. If native offline analytical use cannot be established from those permissions and terms, keep the real issuance unavailable and record the missing decision. Originals, viewing exports and frozen context follow their own existing permissions. [Source policy](../../../internal/geoenv/catalog.go) · [Viewing issuance](../../../internal/geoenv/viewing_package.go) · [Context terms](../../../internal/geoenv/context_dependencies.go)
2. Add an opt-in kit output to the receiver. Write selected files to private temporary storage, verify them, then publish the complete inventory and files atomically on the same filesystem. A retry resumes only against the same trusted identity or restarts cleanly. Reject a changed pin, missing dependency or expired issuance. Keep the existing receiver command and receipt format usable.
3. Ship a locked reader environment, a short operator guide and an example from receipt through native sample. Compose the prepared and handoff validators. Isolate each profile verification in its own process until the legacy binding overrides can be removed compatibly. A native-only kit can open without a viewer, database, network or source rebuild archive. Check expiry before serving local reads and document deletion under the issued terms. A disconnected copy learns about an early withdrawal when it reconnects.

**Acceptance.** With an empty cache and networking disabled, a second receiver verifies a permitted kit and reads the expected sample and feature ID. Corrupt archive, missing selected display, expired terms, unknown required schema and interrupted final write each yield a specific failure. A concurrent verification of two different profiles returns the correct result for each. Test fixture acceptance and real Riyadh issuance are recorded separately. **Depends on** the existing release path, P01 operation definitions and a minimal P03 read for the end-to-end demonstration.

## P06 — Time-aware environmental fields

**Analysis.** The retained ERA5 pilot already contains a 7 × 7 grid, two pressure levels, three variables, an explicit UTC instant and a below-ground mask. Its validator checks the coordinate axes, units, source receipts and sample bounds. This is enough to validate a field reader without acquiring another product. The November 17 source review identifies additional weather and warning candidates that can later enter the same path. [Field validator](../../../scripts/data/observation_formats.py) · [Pilot evidence](../../../docs/implementation/RIYADH_OBSERVATION_PILOT.md) · [Source review](../../../docs/data/WORLDMONITOR_SOURCE_REVIEW_2026_11_17.md)

**Implementation.** Environmental data engineering adds an adapter to P03 for an exact variable, native cell, pressure level and valid time. Return the native value and unit, mask state, source edition and temporal meaning. Declare which timestamps exist for each product, including observation, issue, validity and platform availability where applicable. Preserve the distinction between an observation known by a cutoff and a modeled value valid at an instant. Let P01 designate layers as dated background or require a common validity window. Treat unknown intervals and missing samples explicitly.

**Acceptance.** Compare selected pilot values with an independent decode of the retained source or its recorded control samples. Cover reversed latitude order, a below-ground cell in a fixture, valid zero, missing value, unavailable hour, and a request in metres against the pressure axis. Offline and installed readers agree. A mixed-year release passes a declared background-use profile and fails or remains unqualified for a strict common date according to its evidence. Interpolation, further variables and new providers each require a named use and validation method. **Depends on** P01 time rules, P03 reader, P04 controls and P05 to distribute the chosen subset.

## P07 — Static model metadata and derived assets

**Analysis.** The geographic display registry binds artifacts to their release and input members. The historical model registry already validates axes, units and bounds, but its upload policy requires simulation licensing and perpetual archive permission. A map-only geographic asset must remain usable under its actual source terms. Reuse the applicable validation fields and preserve the existing access boundary. [Display registry](../../../internal/geoenv/display.go) · [Geographic GLB checks](../../../internal/geoenv/display_glb.go) · [Historical model contract](../../../internal/modelassets/domain.go)

**Implementation.** Asset and geographic engineering add a purpose-specific description to authorized geographic derivative metadata. Start with the terrain GLB. Record parent members, recipe/toolchain, units, axes, local origin, bounds, rendering adjustments and feature mapping where applicable. For older releases populate only facts established by a known recipe and exact bytes. Leave ambiguous fields unknown. Expose purpose and limitations through P01, P05 and the existing metadata view. Inventory raw and derived representations separately. Any additional computational derivative gets a new recipe identity, source authorization, comparison method and declared error budget.

**Acceptance.** Load an owned asymmetric shape of known dimensions and check the orientation, origin, scale and bounds independently. Resolve the exact source member from a terrain display. A native-ground request rejects a visual-only derivative. Run these checks on both current and legacy representations. Asset inventory and visual-purpose qualification complete the first delivery. Specialist derivatives remain conditional on a later use. **Depends on** P01 representation meanings and P04 fixtures. Enriched P05 packages can then include these descriptors.

## P08 — Workload measurement and commissioning

**Analysis.** Existing evidence covers metadata load, preparation workers, viewer frame time and paired restore. A receiver experiences a different workload when verifying an archive, opening GDAL, reading scattered native cells and fetching bounded feature sets. The existing evidence supplies comparison data and recovery machinery. The new measurements must follow that actual consumer path. [Installed measurements](../../../docs/implementation/COASTAL_MOVING_AND_READINESS.md) · [Release and recovery evidence](../../../docs/implementation/RIYADH_RELEASE_RECOVERY.md)

**Implementation.** Operations and QA instrument milestone 1 and qualify milestone 4. Fix the release, reader build, machine, process/cache state, query list, concurrency, repetitions and permitted dependencies in a workload file. Include an owned CI workload, the bounded Riyadh candidate and a second frame such as Al Ain. Measure cold verification/open time, warm native-read and feature-query p50/p95, peak RSS, bytes read, temporary disk and cleanup after cancellation. Separate transfer, verification and query timings. Report errors and sample counts alongside percentiles. Establish initial budgets from a baseline and consumer needs, then freeze them before the independent acceptance run. Reopen the design only for a measured bottleneck.

**Acceptance.** Run the fixed query list against the verified local kit and the installed path. Restore the paired database and object snapshot in isolation, reapply later rights decisions, then repeat with the same release and reader pins. Compare semantic results and resource budgets. Exercise over-quota, permission loss and interrupted publication. Leave one evidence record per candidate with machine/build/configuration, hashes, commands, measurements, failed or skipped cases and the receiver's decision. Record an unmet threshold as a failed gate for that workload. **Depends on** P05, P03 and the optional capabilities that the chosen profile actually requests.

## Rollout and handover

- **Installed acceptance runs alongside engineering.** The project record lists shared migration 58, an incomplete F09 observation and a migration 59 rehearsal in isolation. Operations should refresh that record before rollout. Follow the documented order for the pinned observation, authorized release decisions, paired backup and shared upgrade. Building the owned fixtures and reader in an isolated environment can start immediately. Real Riyadh portable use requires the applicable release and source decisions. [Acceptance sequence](../../README.md#next-acceptance-steps)
- **Deploy readers before new producers.** Introduce additive API schemas and scoped storage, publish the compatible reader, then enable the new assessment and derivative producers by profile. Include every new worker module and its dependencies in the toolchain identity. Retain the old processor for verified rebuilds because the base toolchain includes its source-file digest. If a new producer fails qualification, stop issuing its profile and keep earlier readers and release bytes available. [Preparation toolchain](../../../scripts/data/environment_library.py) · [Existing publication contract](../../../internal/geoenv/display_build.go)
- **Use the existing verification entry points.** Extend the geographic PostGIS integration case for release policy, current rights and idempotent publication. Run the existing profile-specific Python checks plus the new reader's independent fixtures. For API changes run `task contracts:openapi` and check the generated client. For changes visible in the Environment Library, exercise its existing browser entry point. Keep raw licensed inputs and individual control records in scoped storage and commit redistributable fixtures and permitted result summaries. [Geographic integration test](../../../internal/integration/geographic_environment_test.go) · [Build and contract tasks](../../../Taskfile.yml) · [Environment Library browser checks](../../../apps/operator-ui/tests/e2e/environment-library.spec.ts)
- **Hand over one reproducible example.** Deliver the consumer request, permitted kit, trusted pins, native query examples, reference answers, suitability report and commissioning record together. Record unsupported claims, any outstanding rights or control-data decision, and its responsible role. The receiving team can then tell which inputs are ready for its intended use and exactly what additional evidence it would need.
